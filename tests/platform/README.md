# Кроссплатформенные испытания BuildWheel

Инфраструктура находится в ветках test/platform-compatibility и feature/android-desktop-input. Перед испытаниями SHA-256 runtime-файлов сравниваются с [source-lock.json](./source-lock.json), привязанным к коммиту проверяемого кода. Workflow реагирует только на эти две ветки; Android job выполняется только в Android-ветке. Права GITHUB_TOKEN: contents:read; публикаций, merge и релизов в workflow нет.

Матрица: ubuntu-24.04 x64, macos-15-intel x64, macos-15 ARM64, TemurinJava25. Используется официальный Mindustryv160.7 JAR; SHA25636d94941a1639478ad1d9be25a9d802c6f77552f400c6da0338b7b019f63a0d1 проверяется до исполнения. Нативные библиотеки берутся из него штатным загрузчиком Arc. Дополнительный Linux-сценарий проверяет системную SDL, отключая предварительное извлечение libSDL2.so через предусмотренный Arc флаг SDL2_STATIC. Название этого флага не означает, что мод пересобирается статически.

## Уровни проверки

1. StartupHarness: настоящий JVM целевой ОС, Rhino и Arc-виджеты, весь граф текущих JS-модулей. Графика/аудио/окно/контент имитированы. Проверяются заводская загрузка EN/RU, регистрация обработчиков, UI, отсутствие FFM при загрузке и сохранённом relativeMouse=true. Пользовательские и повреждённые Settings читаются повторно в новом JVM без заполнения заново. Проверяются независимые значения по умолчанию, корректные соседние и скрытые слоты, точные исходные типы Settings и неизменные байты существующей библиотеки. ClassCastException теперь всегда провал проверки.
2. NativeProbe: настоящее окно/GL/SDL/FFM и текущий sdl-relative.js. Backend-only не исполняет адаптер и не меняет relative mode. Normal проверяет подтверждение образа/GL-окна, warp, чужой режим,3 цикла begin/sample/end, resize, minimize/focus, dispose, курсор и память. Forced-warp должен безопасно отказываться. Linux automatic-warp использует отдельную настоящую SDL2.0.10, собранную с --disable-video-x11-xinput: при hint=false прямой SDL setter обязан принять fallback, а BuildWheel — отказать до захвата, сохранив обычный warp. Архив SDL и загруженный файл имеют собственные контрольные суммы; эта сборка не подменяет проверки штатной SDL игры.
3. GameSmoke: запускает настоящий DesktopLauncher и копию мода в новом профиле. Проверяет заводской профиль, повреждённые Settings и повторный новый JVM без перезаполнения. После реального ClientLoad находит зарегистрированный пункт меню, открывает Радиальное меню и рисует его не менее3 кадров/3 секунд. В вариантах восстановления проверяет исходные типы, корректные соседи/скрытые слоты и неизменные байты библиотеки до ClientLoad и после штатного завершения. Сохраняет screenshot. Графика, загрузчик модов/скриптов и контент здесь не имитированы. Это проверка загрузки и редактора, не всего игрового процесса/строительства.

Для Wayland дополнительно есть отдельный raw-SDL компонентный сценарий. Он создаёт настоящее SDL-окно/GL-контекст, обрабатывает настоящую очередь SDL и исполняет неизменённый адаптер через FFM, но использует фасад размеров Core.graphics и отдельный Application вместо SdlApplication. Это позволяет исследовать SDL/FFM при обнаруженной ошибке штатного Arc GLEW. Сам Arc и игра таким способом не исправляются; успешный raw-SDL тест не считается совместимостью Mindustry с Wayland.

## Графическая среда

Linux: Xvfb + Openbox + Mesa llvmpipe. Wayland отдельно запускается в Weston X11 backend с настоящим input seat. XTest/xdotool передаёт движения через настоящий X-сервер и, для Wayland, через настоящий compositor/protocol. Это синтетический источник, а не физическая мышь.

macOS: используется графический сеанс runner и -XstartOnFirstThread. Pointer.swift проверяет CGPreflightPostEventAccess, активирует только процесс пробного приложения и при разрешении отправляет CoreGraphics HID events. TCC не изменяется. Нет разрешения/GUI/дельт — ограничение или безопасный отказ, не доказательство работающего ввода.

## Запуск

Workflow: .github/workflows/platform-compatibility.yml. Каждый push тестовой инфраструктуры в разрешённую ветку запускает матрицу. workflow_dispatch добавлен для будущего ручного запуска; GitHub может требовать наличие workflow в defaultbranch, поэтому основной способ здесь — push тестовой ветки. Main для этого не меняется.

Ручной запуск на Linux/macOS с JDK25 и зависимостями из workflow:

    python3 tests/platform/run.py --output /absolute/disposable/directory

Все настройки, сохранения, временные библиотеки и crashlogs помещаются в указанный каталог. Runner не открывает профиль установленной игры. GameSmoke получает отдельную копию mod.hjson/scripts/bundles/sprites/sounds.

Для локального GameSmoke на Windows обязательно задавать APPDATA внутри временного профиля; стенд откажет без этого. Также перенаправлять LOCALAPPDATA и -Duser.home. Одного mindustry.data.dir недостаточно для ранних logger/IntelGpuCheck самого DesktopLauncher. Дополнительные свойства -Dbuildwheel.smoke.recovery=true и -Dbuildwheel.smoke.restart=true включают повреждённый профиль и повторный процесс соответственно; restart не записывает тестовые значения заново.

## Интерпретация

- COMPONENT_* — успешное исполнение конкретных нативных компонентов, с указанными ограничениями.
- FULL_GAME_CLIENTLOAD_EDITOR_RENDERED — настоящий клиент/мод/редактор отрисованы и штатно закрыты.
- SAFE_REFUSAL_* — адаптер безопасно отказал; relative mode не сертифицирован.
- INFRASTRUCTURE_* / GAME_OR_INFRASTRUCTURE_FAILURE — нужна причина из журналов; не приписывать автоматически моду.
- CONFIRMED_COMPONENT_DEFECT — конкретная проверка адаптера нарушена; учитывать контекст forced-warp и способ генерации событий.
- PASS_RECOVERY_AND_PRESERVATION — загрузка пережила повреждённые поля, сохранность Settings и библиотеки проверена; графика остаётся имитацией.
- INCONCLUSIVE_NO_OBSERVED_MOTION — движение не наблюдалось; отсутствие мыши/разрешения не превращается в pass.

Результаты, команды, версии, адреса/образы библиотек, SDLerror, JSONL этапы, screenshots и hs_err сохраняются как GitHub Actions artifacts14 дней. Полный игровой JAR и дерево сборки тестовой SDL в артефакт не загружаются. Зелёный job не равен сертификации всей платформы. Повреждённые настройки и fallback не исключены из критериев ошибки. Отдельные известные отказы штатного Wayland/GLEW сохраняются и могут оставить Linux job красным.

Нет испытаний физического устройства, всех compositor/GPU, полного строительства, multiplayer или всех сочетаний других модов.

## Исследование F-02

input-order.js использует тот же StartupHarness и исходную fixture до завершающих проверок. Дополнительный аргумент entry-script позволяет выполнить диагностический сценарий без копирования проекта или изменения рабочего кода.

Выполняются настоящие SdlInput.handleInput/update, InputEventQueue, InputMultiplexer и текущие main.js/wheel.js. Закодированные JNI-пакеты и накопитель SDL моделируются явно: нативные функции SDL и физическая мышь здесь не проверяются. Обычный выбор использует точку ЛКМ корректно. Для 16 относительных историй воспроизводится выбор по движению после клика: правильные Восток/Юг превращаются в Юго-восток при одинаковых доступных Arc данных. Проверяются relative-only, внешний/внутренний/оба ограничителя, перемещение с удержанной ЛКМ и без неё. Дополнительно шесть путей с ограничителем сравниваются при подаче по кадрам и одним нулевым суммарным вектором: рабочая геометрия получает разные результаты, когда порядок потерян.

F02_INFORMATION_LOSS_REPRODUCED означает успешное воспроизведение нерешённого ограничения, **не исправление F-02**. Падение стенда либо отсутствие ожидаемых наблюдений делает проверку ошибочной; этот сценарий не подменяет штатные проверки F-01/F-03. Результаты и точная граница имитации записаны в input-order-observations.json. Новый транспорт SDL events в мод не внедрялся.

## Граница доказательства F-03

Linux использует только публичные SDL_SysWMinfo и XIGetSelectedEvents собственного XDisplay SDL. В исследованных X11 backend SDL2.0.10,2.30.0,2.32.8 подписка XIAllMasterDevices/XI_RawMotion устанавливается после успешной инициализации XInput2; setter затем принимает настоящий режим именно при этой инициализации. Сопоставление библиотек выполняется до нативных вызовов. Проверка подписки однократная; hint и SDL error проверяются при включении, обработка движения не усложнена.

Это не универсальный getter внутреннего warp-флага. Неизвестные SDL и backend без публичного подтверждения безопасно отказывают только в относительном вводе. Доказательство не охватывает произвольно изменённые vendor-сборки с тем же номером версии или другой мод, меняющий подписки на том же XDisplay. Реальные устройства и их ускорение этим не сертифицируются.

Исходники: [SDL XInput2 2.0.10](https://github.com/libsdl-org/SDL/blob/release-2.0.10/src/video/x11/SDL_x11xinput2.c#L116), [X11 setter](https://github.com/libsdl-org/SDL/blob/release-2.0.10/src/video/x11/SDL_x11mouse.c#L335), [fallback](https://github.com/libsdl-org/SDL/blob/release-2.0.10/src/events/SDL_mouse.c#L931), [публичный контракт XIGetSelectedEvents](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man3/XISelectEvents.3.html).

## Локальный Windows

WindowsNativeProbe наследует только общие диагностические функции. Его CLI совпадает с NativeProbe; поддерживаются normal и forced-warp. Работают настоящие Arc/SDL/FFM, три цикла, обычный warp и освобождение. Инъекция user32 mouse_event разрешена только при принадлежности переднего окна процессу; начальные координаты возвращаются после освобождения. Состояние SDL mode подтверждено внутренними проверками самого адаптера, отдельного неподтверждённого поиска адресов в тесте нет. -Dbuildwheel.probe.inject=false выключает инъекцию. Запускать с явным временным каталогом и внешним тайм-аутом, отдельно от пользовательской игры.

## Android с компьютерным управлением

Цель ветки feature/android-desktop-input — Android с текущим `DesktopInput` и аппаратной мышью/клавиатурой. `Vars.mobile` остаётся true. Компоновка, стили и размеры окон не адаптируются под телефон. Обычный `MobileInput` не запускает горячие клавиши, не перехватывает жесты и не применяет отложенный выбор старого обработчика. SDL/FFM, относительный ввод, ограничители и перенос системного указателя на Android не вызываются; сохранённые настольные настройки остаются в профиле.

[android-model.js](./android-model.js) выполняет настоящий граф JS/Arc-виджетов на хостовой JVM с моделями Android-обработчиков и публичного `Os`. Проверяет три логических размера сцены, переназначение клавиатуры/мыши, переключение обработчика, сохранность данных, строгий UTF-8, атомарную замену/резервную копию, отказ доступа и записи, миграцию, формат настольного JSON и повторный процесс. [AndroidModelSupport.java](./AndroidModelSupport.java) запрещает `File.toPath`; фасад JS запрещает обращение к `java.nio.file`. Это не испытание Android syscalls или ART.

[AndroidCtrlModel.java](./AndroidCtrlModel.java) и [android-ctrl-model.js](./android-ctrl-model.js) извлекают функцию моста из рабочего кода. Используются настоящий Rhino/JavaAdapter/Synchronizer/рефлексия и модель очереди AndroidInput. Проверяются порядок Ctrl/цифры/отпусканий, обе стороны Ctrl, MobileInput, смена обработчика, pause/dispose, уже исправленный backend, повторы и безопасное завершение после ошибки. Исправленный в Arc аппаратный Ctrl не переназначается.

Отдельный Android job использует [android-ci.py](./android-ci.py), [launcher hook](./android-probe.java.template) и [android-probe.js](./android-probe.js). Во временном каталоге runner собирается debug APK из Mindustry v160.7 (17012d61d9e4c3cbd9820d87e81c24495486ac53), Arc 7445105cd2, с упакованными sprites/fonts закреплённого официального JAR. Gradle wrapper 9.3.1 заменён на 8.2.1 для AGP 8.2.2; runtime-код игры/Arc не изменяется. Hook и тестовый JS добавлены только в испытательный APK, код мода копируется по проверенным SHA-256.

Эмулятор API 30 x86_64 проверяет настоящее Android/ART, View/AndroidInput, нативную графику, Rhino, UI и файловые операции. Аппаратные события синтезируются через Android View; отдельные виджеты активируются `fireClick()`. Три новых процесса запрашивают 1280×720, 1600×900, 1920×1080, сохраняют screenshots и фактические физические/логические размеры. Это не испытание Google Play Games, физических устройств, сенсорного управления или всех Android API/ABI. Ошибки сборки, SDK/KVM/графики отделяются от ошибок мода.

На Android игра сохраняет мобильное главное меню даже с `keyboard=true`: штатного настольного подраздела «База данных» там нет. В рамках задачи он не создаётся; редактор доступен по сочетанию клавиш и через существующую кнопку меню паузы.

### Диагностика пользовательских назначений Android

[android-keybinds.js](./android-keybinds.js) добавляется только в испытательный APK. Первая стадия выполняет 120 сочетаний: Shift/Alt/Ctrl × две назначенные стороны × две физические стороны × десять цифр. Второстепенный модификатор принимает обе стороны своего семейства; основная клавиша различает стороны. Дополнительно проверяются назначение всех сторон через существующее окно, произвольные F2+U/F3+I/F4+O для колеса/редактора/палитры, отдельные клавиши, отсутствие нужного модификатора, отключение, «Назад» и штатные кнопки сброса. Новые назначения Android не регистрируются: используются существующие шестнадцать `KeyBind` и их `save()`.

Два возвращающих `false` наблюдателя обрамляют существующий обработчик BuildWheel. При MobileInput сравнивается число дошедших до и после него событий down/up; отсутствие перехвата проверяется вместе с отсутствием открытого колеса/окон. События посылаются через реальный Android View с метаданными конкретной стороны модификатора; ожидание учитывает завершение очереди AndroidInput по идентификаторам кадров. Трасса raw/Arc и диагностические результаты сохраняются в `result.json`. Ошибки отдельных назначений собираются, а не превращаются в пропуск оставшихся сценариев.

Исходные значения и типизированные записи Settings сохраняются отдельно, восстанавливаются и сравниваются. Между стадиями оставляется проверяемый набор универсальных назначений: два новых процесса проверяют автоматическую загрузку и действительно открывают все три действия сохранёнными комбинациями. Последняя стадия восстанавливает исходные назначения. Эти проверки подтверждают конкретные синтетические события эмулятора API30; они не проверяют раскладки/системные перехваты клавиш физической клавиатуры или Google Play Games.

### Позиция курсора после закрытия колеса

[cursor-release.js](./cursor-release.js) проверяет настоящий код выбора/закрытия и Arc-сцену с моделируемым SDL-провайдером: оба ограничителя, их сочетание, relative-only, возврат в центр вкл/выкл, успешный выбор, пустой сектор, ПКМ, Escape и потерю фокуса. Отдельно компилируются исходные функции освобождения адаптера с моделями FFM handles: pre-warp/off/post-warp, сохранение видимости, отложенное Cocoa-освобождение с временно невалидным listener, ошибки переноса/окна/setter, сохранение ресурсов при ошибке Cocoa, чужой режим и внешнее выключение. Прямой eval с локальными декларациями не используется: его ошибки областей видимости Rhino не должны подменять испытание обычных функций. Проверяется также реальная Windows DLL из закреплённого JAR: известный хеш, автоматический поиск после безопасного изменения padding и отказ при порче handler/public wrapper/DynAPI.

Нативные стенды закрывают три relative-сеанса в разных асимметричных дробных точках и проверяют Arc сразу, SDL после обычной следующей обработки событий, сохранение точки после повторного end и обычный перенос без включения режима. Windows дополнительно измеряет фактический системный указатель через проверенные user32 getters. Linux/macOS используют необязательный публичный SDL_GetGlobalMouseState из того же образа и калибровку смещения после обычного warp, учитывающую Retina/рамки окна. Отсутствие проверенного getter/калибровки явно отмечается как ограничение, а не успешная физическая проверка. Дополнительного PumpEvents нет. В Android-модели и реальном APK настройка возврата включена при выборе блока: проверяются прежняя позиция, выбор и отсутствие подготовки настольных адаптеров.

Порядок end включает предварительный перенос, отключение режима и завершающий перенос в том же вызове. Последний необходим для Cocoa2.0.16 и старого X11; между отложенными попытками курсор не скрывается. No-flicker, физическая мышь, Retina/несколько мониторов и все оконные менеджеры требуют ручного испытания. F-02/F-04 этим не объявляются исправленными.
